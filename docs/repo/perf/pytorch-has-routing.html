nwsapi / MODEL GUIDE

Two ways to search.
A model helps choose.

First, nwsapi uses its existing rule to choose a search direction from candidate counts. For some :has() queries, a small model trained with PyTorch can recommend a different direction. Both routes check the selector exactly and return the same elements.

At a glance

What A trained function recommends a route. nwsapi checks the matches. Why Searching down or up the DOM can do different amounts of work. When It can switch eligible queries from searching down to up. Where PyTorch trains it. JavaScript runs it inside nwsapi.

What

is the model?

The model is a small function that recommends a search route. PyTorch learns its weights—numbers in the function—from measured examples. Queries run the saved function in JavaScript. Exact selector checks still decide which elements match.

Search down (forward): card ↓ warning. Search up (inverse): warning ↑ card. Both routes return the same matches.

A witness satisfies the condition inside :has(). data-ok="1" is this benchmark’s sample attribute filter.

            Look closer at the training examples
            

              
              

                
              

              

              

                
              

              

              

              

              

                

                

                  The model predicts a route from the query inputs. The trainer
                  compares that prediction with the measured route costs. It
                  calculates a loss that measures the cost of that choice.
                  AdamW, the optimizer, adjusts the weights to reduce this loss.
                  The examples all tune the same function.
                

                

                  The trainer uses repeated timing samples to check uncertainty.
                  It can ignore uncertain comparisons and penalizes large
                  slowdowns more heavily. It also accounts for the estimated
                  cost of calling the model.
                

                

                  Different DOM shapes can have the same model inputs and
                  different route costs. The model cannot see those differences.
                  Validation selects the saved model and threshold. Separate
                  evaluation examples and complete query timings check the
                  result.
                

                
                  Read the loss and optimizer code
                  
                
              

              

                The shorter timing bar is only part of the training signal. The
                trainer also accounts for the existing route, model overhead,
                uncertainty, and the cost of slowdowns.
              

            

          

          

            How training is checked
            

              

                
Training examples

                

                  Teach the function using query facts and measured route costs.
                

              

              

                
Validation examples

                

                  Select the saved model and threshold using separate fixture
                  families.
                

              

              

                
Evaluation examples

                

                  Check the selected model on reserved examples. Complete query
                  measurements are still needed before shipping a performance
                  change.
                

              

            

          

          

            Training happens during development. Queries use
            fixed weights, so your page does not train the model. Updating it
            requires a new training run, review, export, and build.

            Why can one direction be cheaper?
            

              Searching down can stop inside a card as soon as it finds a
              witness. Searching up starts with the witness candidates and marks
              ancestors, which can avoid repeatedly searching inside cards.
              Candidate counts, selector filters, and DOM shape affect the work.
              Counting the visible arrows alone does not predict query time.

When

          

            can the model change the route?
          

          

            The existing count rule chooses the default route. If a query passes
            the eligibility checks, the model can switch it from searching down
            to searching up. Both routes return the same exact matches.

            Calculate the route recommendation
            
    
            
    
            
    
              
    
                
                
                
              
    
              
    
                
    Six inputs, all available before searching
    
                
    
                  The model reads two separate filter flags. Saved means and
                  scales normalize the inputs so their different units are
                  easier to train on.
                
    
                
    
                  
    
                    
                      
    
                        Query fact
                        Raw input
                        Normalized input
                      
    
                        
                    
                  
    
                
    
                
    
                  normalized = (input − savedMean) / savedScale.
                  The exporter folds this calculation into its coefficients. The
                  runtime does not need a separate normalization pass.
                
    
              
    
              
    
                
    Multiply by weights and add a bias
    
                
    
                  A weight is a multiplier. A bias is the starting value of the
                  sum. Chromium makes four intermediate sums, then ReLU replaces
                  any negative sum with zero. jsdom goes directly to one linear
                  score.
                
    
                
    
                
    
              
    
              
    
                
    Compare the score with a saved threshold
    
                
    
                  Chromium combines the hidden values using another set of saved
                  weights. jsdom already has its score. A value above the
                  threshold recommends searching up. Otherwise, the search
                  continues downward.
                
    
                
    
                
    
                
    
              
    
            
    
            
    
              The calculator uses the committed
              {host}-weights.generated.json files and your current
              inputs. Displayed values are rounded. The route recommendation
              comes from the generated function.
            
    
            
              Compare with the generated JavaScript
              
            
          
    
          
    
            What if the model picks the slower route? A poor
            recommendation can increase query time. Both routes still use exact
            DOM checks and preserve result order. nwsapi does not
            detect a slower recommendation and retry the other route. Training,
            validation, and benchmarks reduce this risk without guaranteeing
            every choice is faster.
          
    
          
    
            When does it fall back to the existing route?
            
    
              Unsupported queries keep the existing route. If the optional
              callback throws or returns anything other than true,
              the downward search continues. If the count rule already chose
              upward search, that choice stays. These guards handle unsupported
              inputs and callback failures. A valid recommendation that turns
              out to be slower still runs the recommended route.
            
    
            
              See the guards and exact matching code
              
            
          
    
          
    
            Model terms and arithmetic
            
    
              
    
                
    Model
    
                
    
                  A function with numeric parameters learned from measured
                  examples. Here, it returns a boolean route recommendation.
                
    
              
    
              
    
                
    Policy
    
                
    
                  A rule for choosing an action from the available facts. Here,
                  the action is whether to switch from searching down to up.
                
    
              
    
              
    
                
    Inference
    
                
    
                  Calling the trained function. Ordinary JavaScript multiplies
                  inputs by saved weights, adds them, and checks a threshold.
                
    
              
    
            
    
            
    Hidden units and the output
    

            
    
              A hidden unit makes an intermediate number from the inputs.
              Chromium uses four of these, each with a ReLU operation that
              replaces a negative value with zero. Their weighted outputs
              produce a final score. The saved jsdom model has no hidden layer.
            
    
            
    hidden = Math.max(0, bias + weight1 * input1 + …)
score  = outputBias + outputWeight1 * hidden1 + …
override = score > savedThreshold
    
            
    
              A weight multiplies an input. A bias adds a constant. Training
              adjusts both. The output recommends a route. It does not predict
              whether an element matches or express a probability. Queries run
              in JavaScript without Python, a GPU, or a remote model.

    Where
    
          
    
            does the model run?
          
    
          
    
            The model runs inside the nwsapi bundle. PyTorch is
            only needed during training. Repository scripts export its saved
            weights to JavaScript and generate a typed module. The build
            includes that fixed module in dist/nwsapi.js.

            Use the model or rebuild its module
            
    // An `nwsapi` instance created directly for jsdom:
engine.useNeuralPlanner('jsdom')
const matches = engine.select('.card[data-ok="1"]:has(.warning)', document)

// Disable calls to the selected policy:
engine.configure({ NEURAL_PLANNER: false })
    
            
    
              New nwsapi instances select the Chromium policy by
              default. The jsdom adapter selects its own profile. Existing query
              calls stay the same. To rebuild from the committed JavaScript
              exports:
            
    
            
    pnpm run gen:has-route-decision
pnpm run build
    
            
    
              These commands do not retrain the weights. The training entry
              point is pnpm run bench:planner:dispatch:train, with
              input and output arguments. Read the trainer and setup
              documentation before starting an expensive training run.
            
    
          
    
        
    
        
    
          
    What the evidence currently supports
    
          
    Measure the whole query
    
          
    
            Both routes preserve exact matches and document order. The model can
            still slow a query down, including the cost of its checks and
            callback. Recorded synthetic tests show both speedups and slowdowns.
            They do not establish a general speedup or show that the model beats
            a simpler fitted rule.
