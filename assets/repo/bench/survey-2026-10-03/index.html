Further v3 performance opportunities

Audited prerelease/3.0.0 at e988a9a on October 3, 2026. The package manifest still labels this development build 2.3.0-prerelease. The charts preserve that actual version and identify the bundle by SHA-256. This follow-up adds measurement and chart tooling. It does not change the selector runtime.

Findings to act on

Priority Opportunity Evidence Next implementation and acceptance condition
1 Stream positions across mixed sibling types A warm main > :nth-of-type(2n) query makes 4,102, 16,390 and 65,542 sibling reads for 64, 128 and 256 siblings with four alternating types. At 256 siblings of one type, it makes only 262 reads. Replace repeated type-list reconstruction with a per-query parent table keyed by namespace and local name. Forward positions can use incremental counters. Reverse positions need totals or a reverse pass. Preserve the existing cheap homogeneous path and bound allocation to the query.
2 Add optional jsdom implementation-node traversal The latest host supplies only idlUtils. The adapter's optional domSymbolTree readers are never installed through that constructor. Treat this as a capability-detected enhancement. Missing, throwing or incompatible probes must leave ordinary DOM traversal working. Enable readers independently, preserve wrapper identity, and fall back for unsupported nodes. Require the graceful fallback contract below before landing.
3 Reuse an attribute load within a pure compound [data-value^="foo"][data-value$="bar"] performs two reads. [data-value="foobar"][data-value] performs one value read and one presence read. Exact duplicate equality tests already collapse to one read. Give a compound a small attribute-load table. Load once, lazily after cheaper guards. Reuse only for the same element, namespace and name. Derive presence from value !== null, preserving empty values. Disable for extension or legacy semantics that can observe read order.
4 Reject irrelevant stylesheet rules before matching A simple-class subject prototype lowers check() calls from 9,477 to 2,994 on 241 rules and 24 styled elements. Coordinate stylesheet subject-cache invalidation with the host before enabling selective extractSubjects(). The current upstream mutation contract blocks a safe general rollout. See the reproduction below.
5 Balance sparse type-union merging lookup/tag.mts merges each new collection into the accumulated output. Later merges recopy earlier nodes and repeat document-order comparisons. Reuse the balanced-merge strategy already present for other selector groups. Start at four or more nonempty collections. Retain the existing dense broad-scan route and periodic density probe. Compare interleaved, disjoint, tiny, sparse and dense unions.
6 Share mixed-chain constants with the factory compile/mixed.mts compiles recursive helper predicates without the outer compiler context. The greedy predicates receive that context. Inspect emitted class/attribute expressions and hoist reusable regex constants into the factory prelude. Measure fallback-heavy misses separately from greedy hits. Audit helper-local variables and avoid making constants engine- or document-bound.
7 Compile expensive forms only after reuse pays for them The previous port measured about 20% higher short-selector cold compilation time while adding warm execution wins. pure.mts analysis is also repeated by several planning paths. First share one bounded pure-selector analysis across those paths. Then try a compact first-use plan and promote only eligible reused selectors. Full syntax validation must still happen on the first call. Compare cold application startup, churn, many documents and sustained hot queries.

The first three are the recommended next implementation batch. The read counts are measurements of current work, not promised speedup factors. The type-position fixture shows approximately quadratic traversal growth. A replacement still needs timing, allocation, mutation and namespace evidence before landing.

Relevant implementation: type positions, position routing, host readers, attribute compilation, guard ordering, type unions, mixed chains, factory cache.

The audit distinguishes these gaps from existing optimizations. v3 already has cheap pure guard ordering, exact-token deduplication, grouped candidate scans, ancestor tag masks, bounded relative existence paths, sparse inverse :has() marking, mixed-chain memoization and byte-budgeted compiled caches. Adding a second generic cache or Bloom filter would duplicate some of that work.

Hooks worth using

The host's Document constructor path lazily creates the selector engine and supplies idlUtils. The current adapter already uses those utilities for attribute reads. Keep that lazy boundary. Creating an engine for every document at construction would discard an upstream optimization.

The host now owns DOM tree links. Prefer probing implementation-node getters obtained through the supplied utilities over importing that private tree module or reading _links directly. This also avoids a dependency on the removed domSymbolTree constructor option. A more ambitious implementation-node execution mode could unwrap the candidate once and wrap only final results. That requires a distinct adapter backend and careful auditing of every pseudo-class. It is not a small reader substitution.

The latest Node implementation has versioned collection invalidation and lazy memoized collection queries. A supported host mutation-epoch hook could reduce observer bookkeeping for collection snapshots. Its invalidation domain must be explicit. A tree version does not by itself certify focus, validity, language, hover or other dynamic selector results. Continue caching plans rather than complete query answers.

Required graceful fallback contract

Implementation-node traversal is an optional enhancement. The portable DOM path remains the baseline for every supported host. These are acceptance requirements for the proposed implementation, not claims that the new readers have already landed.

  • Probe lazily, once per adapter capability setup, using detached nodes and the host-supplied utilities. Check parent and sibling identities, element-only behavior around text/comment nodes, and wrapper round trips. Feature detection decides eligibility, not a jsdom version string.
  • A missing utility, unavailable getter, thrown capability probe or unexpected probe result disables only the affected enhancement. Adapter construction and ordinary queries must continue. Successful attribute readers can remain enabled when traversal readers are unavailable.
  • Nodes that cannot be unwrapped by this host, including foreign-realm or adopted nodes, use their public DOM getters. Treat an unsupported conversion separately from a valid null parent or sibling. Never turn a failed conversion into an empty match result.
  • Keep optimized reads behind stable dispatch functions. A detected capability failure can disable that reader and retry the individual pure read through the public getter. Do not replay a whole query after callbacks may have run. Do not blanket-catch selector syntax errors, callback errors or errors from the public DOM operation.
  • Do setup checks outside candidate loops and avoid repeated exception-driven probes on unsupported hosts. Measure the enabled path and disabled path. The fallback must preserve both semantics and inexpensive startup.
  • Before shipping, cover absent, partial, throwing and incompatible utilities, non-jsdom hosts, multiple installed host copies, detached trees, document fragments, shadow roots, adoption, HTML/XML and mutations. Compare ordered element identities and callback behavior with the portable path. Add firstOf only after its separate probe and measurement justify it.

Stylesheet subject filtering: useful, currently unsafe to enable generally

The latest computed-style matcher calls extractSubjects(selector, caseSensitive) and caches its output on the rule. It checks ID, class and tag keys before invoking check(). Our adapter returns a wildcard subject, so every rule remains eligible.

The exploratory probe handles only selectors consisting of one simple class. All other rules retain wildcard subjects. It records seven fresh documents for each mode, with setup excluded. The source is survey/hooks.mts, and the complete observations are hooks.json.

Mode check() calls Median style work
Current v3 adapter 9,477 40.26ms
Narrow subject prototype 2,994 9.45ms
Stock latest host and competitor Not instrumented 7.78ms

These are exploratory, instrumented, fixed-order observations. The count reduction is 68.4%. The apparent 4.26× timing improvement needs an alternating, uninstrumented confirmation. The stock row also shows that the warm query chart does not establish faster style calculation for v3.

The prerequisite is correctness: after a cached rule changes from .missing to .hit, the selectorText setter does not clear _selectorSubjects. Even forcing style-cache invalidation through an attribute mutation leaves the selective keys stale. Both the prototype and the stock competitor return black instead of the expected rgb(1, 2, 3). The current wildcard adapter returns the correct color. The probe records all three results. A host fix should invalidate both style results and subject keys when selector text changes. Do not use a monkey patch of host rule setters as a production optimization.

Once that contract is fixed, extract conservative keys from each rightmost subject. A selector-list branch without a provable necessary key must contribute a wildcard. Ancestor classes, negated classes, unhandled nested logical forms, escapes, quirks folding and namespace rules must not produce false negatives. Share the adapter's parsed selector entry with check() to avoid duplicate parsing.

Compiler and JIT directions

A small plan representation before more string rewriting

Use the conservative pure scanner to produce a bounded plan with candidate seed, compound guards, relations, required attribute loads and estimated traversal work. Emit from that representation once. This gives guard ordering, common-load elimination and logical inlining one consistent view. Unsupported syntax continues through the existing compiler. The aim is to avoid repeated analysis and redundant emitted work without introducing a full second CSS parser.

Query-local feedback and guarded specialization

Candidate counts, witness density, visited ancestors and early-exit rates can choose between existing exact routes. Sample after a small number of queries and use a cooldown before switching again. Never collect telemetry on every element merely to save one cheap guard. Existing type-union routing already follows a similar periodic-probe design.

A specialization key must include HTML/XML mode, quirks behavior, legacy configuration, extension generation, host reader capabilities and callback semantics. Recheck these when binding or invalidating a plan. A stale cost estimate may select a slower exact path. It must not select a stale result or bypass validation. Keep feedback weakly owned and source-byte bounded.

More work avoidance

  • For eligible pure multi-~ relative chains, try a monotone forward cursor that advances through each required witness. Prove it only for the all-general-sibling shape first. Mixed child or adjacent relations can require backtracking.
  • For inverse :has() with no witnesses, return the known empty result before allocating the ancestor-mark map. Consider selecting that route earlier only when a cheap count justifies it. Avoid repeating the small-query candidate-fetch regression found in the prior port.
  • Delay rare fallback helper creation for mixed chains only if allocation measurements show a benefit. Moving helper creation into the hot resolver could create more closures and erase the gain.
  • A bounded cross-engine cache of unbound factories can amortize compilation across many jsdom documents. Restrict sharing to factories with no captured document, engine or host nodes. Measure initialization savings against retained machine code and the existing engine-local cache.
  • Offline selector-shape profiles could tune thresholds without adding any inference to the runtime. Keep adversarial misses, cheap controls, cold calls and mutation-heavy workloads in the tuning set.

WebGPU and an embedded model

gpu-lexer is a useful architecture reference. Its model card describes 41,321 deployed int6 weights and 83.02% agreement with normalized syntax-color labels. It explicitly excludes compilation and parsing from intended uses. Those labels cannot safely replace CSS parsing or selector matching.

Its runtime design provides transferable ideas: compact features, resident resources, compact output and batching. It also accounts for preparation, dispatch and readback. That overhead matters for the microsecond query paths in this report. No GPU benchmark was run in this survey, so no device-specific crossover is claimed.

Ranked by expected payoff for the effort

The first investment should be a reusable CPU cost planner. It can improve several existing exact execution paths with a small integration surface. The rankings below are engineering judgments about benefit, implementation cost, reuse and compatibility. No learned-model, SIMD or GPU speedup has been measured here. The measured sibling traversal fix remains ahead of these research projects in the overall v3 queue.

Rank Investment Scenarios sharing the work Expected payoff and promotion requirement
1 One cost planner, initially rules, optionally an offline-trained decision tree Sparse versus dense :has(), tag-union merging versus broad scans, eligible traversal direction, and whether a reused selector merits a larger compiled plan. Plan choices can serve all-results, first-result and element-match APIs where each route preserves that API's semantics. Highest expected return per unit of effort. Reuse existing exact routes and already available counts. Compare fixed rules with a compact CPU model on held-out DOMs. Include feature extraction, cold initialization and worst-case poor choices. Ship the model only if it adds a repeatable gain over the rule baseline.
2 A shared packed snapshot and exact CPU bitset backend Many selectors over one immutable DOM, necessary-condition filtering for stylesheet rules, repeated DOM analysis, and batched existence queries. High reuse for genuinely batched work, with a larger implementation cost. One topology/ID/class/tag representation can later feed SIMD or GPU execution. Measure snapshot construction, index memory and reuse count. Live stylesheet use remains gated on the host invalidation fix.
3 WASM SIMD for the same packed batches The same batch-query and rule-filter workloads as rank 2, with CPU execution and no GPU device requirement. Incremental experiment after rank 2. Keep the data layout stable so the backend can change without rebuilding the planner. Retain JavaScript when WASM startup, copying or small batches erase the gain.
4 Exact WebGPU execution over the same snapshot Large repeated batches, large DOM-analysis jobs, and broad rule-candidate filtering with enough work to amortize transfers. Higher ceiling but lower near-term return. Requires an optional asynchronous API. Measure upload, pipeline startup, dispatch, readback and ordered reconstruction together. Promote only beyond a demonstrated end-to-end crossover against the CPU and SIMD backends.
5 GPU inference for planning Very large offline batches of plan-selection decisions, if such a workload emerges. Lowest expected return for ordinary selector calls. Reconsider only if the rank-1 CPU model becomes a measured bottleneck and GPU batching pays for synchronization.

Approximate neural lexing or matching is excluded from execution decisions about correctness. A model may choose which eligible exact algorithm to run. It may not accept invalid syntax, drop candidates based on a prediction, or decide that an element matches.

Make the first investment useful across scenarios

Build a small shared descriptor from the existing pure-selector analysis: API mode, host capabilities, relation shape, required guards, candidate count when already available, and observed witness density when cheaply sampled. Each planning decision exposes only its eligible exact alternatives and a default route. Do not scan the DOM merely to populate model features. Unsupported syntax or unavailable features immediately use the existing default.

Use that descriptor for separate decisions under one planner interface. First-result queries value early exit, all-results queries also pay for ordering and materialization, and element matching starts from one supplied node. Keep these objectives explicit. A single model need not make every decision if small specialized rules are cheaper. Share descriptors, measurement records and fallback policy before adding model complexity.

Start with the :has() density decision and sparse type unions because both already have alternative routes and observable counts. Then evaluate traversal direction and compilation promotion. Collect bounded query-level samples only after reuse. Train offline on separate DOM/application families, and include cold, tiny, empty-result, mutation-heavy and adversarial cases. An offline-trained tree can be emitted as ordinary JavaScript branches with no model download, GPU initialization or inference framework.

Share the representation before adding more backends

If batch workloads justify rank 2, use one immutable snapshot representation for CPU, SIMD and GPU experiments. Include node order, parent/sibling topology, interned names and the attributes required by the batch. Necessary-condition bitsets can reject impossible candidates exactly, with the existing matcher responsible for the remaining supported semantics. Dynamic state must either be captured by an explicit snapshot contract or make the batch ineligible.

Keep the planner and packed representation separable. Ordinary synchronous queries can use the planner without paying for a snapshot. Batched callers can amortize one snapshot across query sets, rule filtering and DOM analysis. This gives multiple scenarios a shared investment while allowing an unprofitable backend to be removed independently.

Graceful enhancement and stop conditions

Every planning choice retains an exact CPU default. Load optional WASM/GPU resources only after workload eligibility and capability checks succeed. Missing WebGPU, adapter/device acquisition failure, shader failure or device loss routes an asynchronous batch to its CPU backend over the same valid snapshot. Never silently answer against a different live DOM generation. Discard incomplete accelerated output before returning CPU results.

Adopt a stage only when its end-to-end gain exceeds measurement variability and its initialization, bundle and memory costs fit the targeted workload. Stop at the CPU planner if that captures the useful benefit. Stop at CPU bitsets or SIMD if GPU setup and synchronization do not pay back. Multi-scenario reuse is a promotion criterion, alongside exact result identities, ordering and safe fallback.

Shared methodology and interpretation

The existing 36 selectors cover component, documentation and utility-class fixtures. Both engines run direct library APIs in Chromium 154.0.8037.0 on the same native DOM implementation, with independent identical documents. Native selector identities and ordering are checked before and after timing. Each of nine rounds alternates engine order, warms for 20ms and measures batches of 16 calls for at least 30ms. Setup is excluded. Values are medians of per-round batch averages. Whiskers show observed round ranges, not confidence intervals. The machine was an Apple M1 Max running on battery. This run measures warm queries returning all matches. It does not measure cold compilation, browser-native query speed, jsdom wrapper overhead, style computation, mutation throughput or memory. It compares only the named latest competitor, not every selector engine.

These four form-state cases include the narrowest observed advantage: input:read-write was 68.96µs versus 78.49µs, or 1.14× relative speed. The full set has lower v3 medians in 36 of 36 cases, ranging from 1.14× to 388.04×. The largest ratio is an exact-ID case. These descriptive ratios are not a workload-weighted application speedup or a significance claim. The separate style probe above includes a workload where the stock host is faster.
