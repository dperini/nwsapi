How we train a tiny model for nwsapi

The short version: we measure exact ways to run a selector, then train a tiny decision tree or neural network to predict which route may cost less. The model chooses a route. nwsapi still checks every match itself.

Current state: nwsapi still does not run a neural network in production. We have now trained a real PyTorch network from paired nwsapi route timings and exported an offline JavaScript model. Its held-out results did not improve on the existing guarded rule, and the model adds decision overhead, so it remains a research artifact. See the neural planner report for the measurements and conclusion.
CPU firstTiny trees are easier to train, inspect and deploy than GPU models for microsecond queries.
Exact answersBoth routes use nwsapi’s normal selector matcher and preserve result identity and order.
Fallback alwaysUnknown inputs use the existing known route, and unsupported cases skip the learned preference.
01 / the workflow

From benchmark to a small rule

STEP 1Make test DOMs

Generate varied trees and selectors with known shapes.

STEP 2Measure exact routes

Time the existing and alternate algorithms in Chromium and jsdom.

STEP 3Fit a tiny tree

Choose splits that reduce measured time, not label errors.

STEP 4Check new cases

Evaluate on held-out families the trainer never saw.

STEP 5Keep or reject

Only promote a guarded rule if it passes the preset speed and safety gates.

Separating training cases from evaluation cases matters. If we tune and grade the model on the same DOM shapes, it can memorize those shapes and look better than it will on new pages.

02 / what is being learned

Choose work, never decide correctness

A CSS selector can often be evaluated by more than one exact algorithm. For example, nwsapi can search from a selector’s starting element toward a witness, or it can find witnesses first and mark the related starting elements. Both routes apply the same selector rules; one may simply do fewer operations for a particular DOM shape.

Forward route

Start with possible anchors, then look for matching descendants or relatives under each anchor. It can be cheaper when there are few anchors.

Inverse route

Start with possible witnesses, then walk back to related anchors. It can be cheaper when witnesses are sparse and the eligible anchor set is large enough.

The planner may choose between those routes using cheap facts already available, such as anchor count, witness count and whether the selector has an attribute clause. The matcher still decides whether each candidate really matches. A model cannot make invalid CSS valid, skip an element it merely predicts is irrelevant, or change result order.

03 / training data

What examples go into training?

Each row is a measured situation: a generated DOM, one selector shape, a host runtime, cheap numeric features, and the observed time for each exact route. For the recorded :has() planner, training combined Chromium and jsdom observations. Inputs carry build and fixture hashes so records from different code or DOM generators cannot quietly be mixed.

The fixtures are synthetic. They are helpful for controlling one variable at a time, but do not represent every app. That is why the report calls for real-application checks before broad performance claims.

04 / fitting

What does “teach” mean here?

It does not mean a person types facts into a chatbot. It means our trainer program reads a spreadsheet-like file of examples. Every example says: “Here is the shape of the DOM. Here is how long route A took. Here is how long route B took.” The trainer looks for a short rule that would usually pick the faster route.

A made-up example (just to show the idea)

Suppose one test page has 64 possible anchors and 8 matching witnesses. The forward route takes 20µs; the inverse route takes 8µs. This example teaches the trainer that, for those feature values, inverse was faster. A different page might teach the opposite. The trainer needs many pages so one unusual example does not decide everything.

µs (“microsecond”) is one millionth of a second. The numbers in this example are invented for explanation; they are not a measurement from the report.

Which model did we use?

The original experiment used a small decision tree, implemented in scripts/repo/bench/planner/model.mts. Think of it as a tiny flowchart made of questions. A question might be “Are there more than this many witnesses?” Each answer leads to another question or to a final choice: use forward, or use inverse.

The tree is not a neural network or large language model. It is a few if/else questions, with no neural weights. The fitter tries simple thresholds using measured feature values, keeps a split only when it reduces measured work enough, and stops after at most three levels. It also requires at least six training examples on each side of a split. Separately, section 09 describes the PyTorch neural network trained from paired route timings. The tree remains the simpler production approach because the neural experiment did not improve held-out query time.

What exactly was trained?

  • Type-union experiment: choose between merging several tag result lists and scanning a broader list. It learned one question about candidate density, with a split near 39.4%. Held-out results were too weak, so we rejected it for production.
  • :has() experiment: choose between searching from anchors toward witnesses and starting from witnesses, then tracing back to anchors. The fitted tree was just one final choice—prefer the inverse route in its measured range, with no questions inside the tree. After inspecting slow cases, we added separate safety gates and kept the existing route for attribute-filtered cases.

The :has() model's recommendation was copied into ordinary guarded JavaScript. That code is what production uses. The training JSON and generated .mjs file are experiment records; the runtime does not import them, build a tree, or do any learning.

How does the trainer decide a rule is better?

For each example, it compares both measured times. Then it asks whether a proposed question would lower the combined cost. A choice that takes twice as long is treated as a bigger mistake than one that is only a little slower. It tries candidate feature thresholds, such as different witness counts or ratios, and retains a question only when the overall cost improves enough. Chromium and jsdom times are compared relative to their own fastest route, because the two environments have different baseline speeds.

05 / what happened

One experiment shipped as a guarded rule; one did not

It is useful to see both outcomes. The first tiny-model experiment tried to choose between tag-union routes. Its held-out gains were too small and one jsdom case regressed substantially, so the production rule was left alone. That is a successful experiment even though its model was rejected: it prevented an unproven runtime change.

The :has() model favored inverse witness traversal for a limited, measured domain. A training regression showed attribute-filtered compounds needed different handling, so those retain the original density rule. An exact empty-witness check also exits early before allocating the marking map or visiting anchors. The measured rule is guarded by workload eligibility and falls back outside that domain.

How to read these bars 1.0× is tied with the old route; greater than 1.0× means the new route finished sooner. These figures come from synthetic warm-query cases. They do not promise the same gain for every selector or app.

06 / running it

Reproduce the offline training

From the repository root, the following commands collect training measurements and fit the small tree. The build and browser setup must be available. Keep the output in a new experiment directory so frozen inputs are not overwritten.

node scripts/repo/run.mts scripts/repo/bench/planner/has/run.mts collect assets/repo/bench/planner-has-new node scripts/repo/run.mts scripts/repo/bench/planner/has/fit.mts assets/repo/bench/planner-has-new node scripts/repo/run.mts scripts/repo/bench/planner/has/run.mts evaluate assets/repo/bench/planner-has-new

Collection measures the available routes. Fitting reads only the training rows and creates shared-model.json plus shared-model.mjs. Evaluation measures unseen families and compares the learned choice with the original rule. In the production release workflow, actual-build confirmation, ordered-result identity checks, and broader compatibility coverage are separate gates.

Promotion checklist, in plain words

  • Does it beat the old rule by a useful amount on held-out DOM shapes?
  • Does it avoid large slowdowns on individual cases, including small queries?
  • Does every query still return the same elements in the same order?
  • Can it fall back cheaply for unknown hosts, feature ranges and selector forms?
  • Are setup cost, code size, memory and cold queries included in the decision?
07 / real models and WebGPU

Can we use a model from Hugging Face?

We can use Hugging Face’s GPU building blocks, but its WebGPU Kernels page is not a shelf of ready-made models. It lists small GPU operations such as matrix math. The @huggingface/kernels JavaScript loader can fetch a versioned operation from the Hub and run it. Those operations could help run a neural network that we train, but they do not contain the training examples or learned answers for nwsapi.

Hugging Face also has full models and a Transformers.js runtime that can use WebGPU. The models shown in its WebGPU guide do jobs such as making text embeddings, transcribing audio and classifying images. We cannot point one of those at a selector and expect it to know which nwsapi algorithm is faster. That would require a model trained for our own inputs and choices.

What does gpu-lexer use?

gpu-lexer embeds its own purpose-built neural model. Its browser version has 41,321 compact 6-bit numbers (“weights”) and predicts one of nine syntax-color labels for each piece of source code. A CPU pass first breaks text into simple pieces; the GPU model uses nearby text and wider file context to label them. It is a color highlighter, not a CSS parser or selector matcher, so its weights do not transfer to nwsapi.

The useful lessons are how small the packaged model can be, how the CPU prepares simple input, and how GPU resources are kept around between calls. The project itself warns that starting the GPU and reading its answer back can make tiny jobs slower.

What does gpu-query add?

gpu-query is an experimental app-search parser and a closer deployment example. It has a 29,597-parameter neural model. The same model runs through a TypeScript CPU path or a WebGPU shader. One short request stays on the CPU; WebGPU is used for batches. The project reports identical CPU/GPU answers and increasing speedups as the batch grows on its tested M4. Its weights parse phrases into filters, so again, we would train new weights for nwsapi rather than reuse theirs.

Hugging Face announced 207 versioned WebGPU kernels in September 2026. Their pages include operation descriptions, shader code, correctness examples and benchmark cases. That makes the collection useful if our own model needs a GPU operation that is already covered. The kernels are ingredients; we would still design and train the nwsapi model.

08 / a real nwsapi model

What should we build?

For a real neural-model experiment, train a small neural network specifically to rank exact nwsapi routes. Give it simple numbers that the query already knows—for example, how many candidate elements and witnesses there are, whether the selector uses attributes, and which API is being called. Train it from paired timings: measure each eligible route on the same case, and teach the model which one costs less.

INPUTCheap query facts

Counts and selector shape already available to the planner.

MODELSmall learned network

A few numeric layers produce route scores.

CHOICEPick an exact route

Choose the lower predicted cost within a safe tested range.

WORKNormal nwsapi matcher

The existing engine still verifies every selector match.

FALLBACKKnown CPU route

If the model or GPU is unavailable, use the current algorithm.

One query: start on the CPU

For one selector, a tiny JavaScript network may be faster overall because it avoids GPU startup and result transfer. We must measure this; model execution still has a cost.

Many queries: test WebGPU

If an application plans many queries together, GPU work can run in parallel. Try Hugging Face kernels or a custom WGSL shader only after a batch benchmark shows the end-to-end result is faster.

We should split training and evaluation by whole DOM shapes and selector families, then compare the neural model with the current rule, the small decision tree and always using each exact route. Record slow individual cases as well as average speed. Keep the neural model only if it wins on new cases without adding a costly setup step. A model can pick a slower exact route, but it must never be allowed to change which elements match.

So, are Hugging Face models usable? Their kernels are usable as low-level tools, and their runtimes can execute supported model formats on WebGPU. We have not found a pretrained Hugging Face model that solves the nwsapi planning task. The practical route is to train a small task-specific model from nwsapi benchmark data, first run it on the CPU, then measure batched WebGPU as an optional backend.

09 / build a neural model

A practical recipe, from zero to a measured model

This is the hands-on workflow we implemented for a real neural model. It predicts the cost of each eligible exact route from simple numbers. The experiment runs in CPU PyTorch for training and exports JavaScript inference so we can count its cost. WebGPU remains a separate future experiment because this model decision is too small to justify an individual GPU dispatch.

1. Decide precisely what the model may choose

Choose one narrow question first, such as “for this eligible :has() query, should nwsapi use forward or inverse traversal?” Define the two routes and all safety exclusions in ordinary code. Both routes must already return the same ordered matches. The model only ranks them.

2. Collect paired measurements

For every generated DOM and selector, run both routes against the same unchanged tree. Record the route times, host (Chromium or jsdom), API shape, DOM family, selector family and build/fixture hashes. Warm the runtime, rotate route order, repeat enough times to reduce timing noise, and keep cold-start cost as its own measurement. Never mix data from different builds or fixture definitions.

{ "features": [64, 8, 0, 0.125], "costsMicros": [20.0, 8.0], "routeNames": ["forward", "inverse"], "host": "chromium", "family": "clustered-dom", "buildHash": "...", "fixtureHash": "..." }

Those numbers are illustrative. In the current planner experiment, features already available include anchor count, witness count, selector arity, and whether attributes are involved. A feature is allowed only if production can compute it cheaply before the choice. Avoid adding a DOM scan just to feed the model: that scan could cost more than the work it saves.

3. Make the training target “how long will each route take?”

This first network predicts a time for each route instead of directly guessing a route label. For one example, its target is the pair of measured costs: forward took 20µs and inverse took 8µs. We train it to predict both numbers, using log time so proportional mistakes matter. At query time, the planner chooses the route with the lower predicted time. We still grade the choice by the actual time saved or lost on held-out cases.

4. Keep whole families for the final exam

Split examples by DOM and selector families before training. Keep some shapes entirely unseen until the final evaluation. Otherwise near-duplicate generated trees can leak into both groups and make the model appear more capable than it is. Keep one final locked evaluation set and do not repeatedly tune against it.

5. Train a small network on an ordinary computer

Use Python 3.12 with PyTorch 2.14.1 to train a tiny feed-forward network: a few input numbers, one small hidden layer, and one output score per route. Normalize the numeric inputs using training-set statistics, record those values, and export the learned weights. CPU training is enough for a dataset of this size; a GPU is optional and does not make the examples better. Hugging Face kernels are optional low-level operations for running supported GPU math, not a training dataset or a pretrained nwsapi brain.

PyTorch is a development-only dependency in .config/model-training/, pinned in .config/external-tools.json and locked with uv.lock. It is not installed for nwsapi users and is not part of the JavaScript runtime. From the repository root, install the pinned Python environment with:

pnpm run setup:model-training

This command installs the repository-pinned uv tool if needed, prepares Python 3.12 in the ignored .config/model-training/.venv/ environment, installs the locked PyTorch and NumPy packages and verifies PyTorch’s version. The end-to-end command pnpm run bench:planner:neural rebuilds the frozen dataset from the checked-in route measurements, trains the network, measures its JavaScript decision overhead, and creates a chart report. The training project remains development-only.

Why PyTorch, and are there better tools?

PyTorch is a practical first choice for training and experiments, not a requirement. It makes it straightforward to define a tiny network, calculate how wrong its guesses are, adjust its weights, and save those weights. Its tutorials also cover exporting a trained model to ONNX, a format that other runtimes can read. We can keep PyTorch on the developer’s machine and still ship only a small JavaScript inference function and numbers.

ToolWhere it fitsTradeoff for nwsapi

Hand-written JavaScriptRun the exported weights with a few multiply-add operations.Likely the smallest and fastest production inference path; inconvenient for training, so generate the numbers offline.

Where Transformers.js fits: Transformers.js runs supported Hugging Face model architectures in a browser or Node.js. It uses ONNX Runtime, can run on CPU, and can use WebGPU when supported. You can also convert your own trained PyTorch, TensorFlow, or JAX model to ONNX. But Transformers.js does not train the nwsapi model for us, and its ready-to-use pipelines target tasks such as text, image, and audio processing. Our planner has a few numeric inputs and predicts one of two routes, so it would need a model trained for that purpose and a compatible model graph. We could use Transformers.js or ONNX Runtime to test that graph, but if the model is tiny, a few generated JavaScript multiply-adds may be smaller and faster. Treat Transformers.js as a useful experiment/runtime option, not an automatic production dependency.

There is an even simpler baseline: use the existing decision tree or fit a small linear cost formula. Since nwsapi’s planner has only a few numeric inputs and two route choices, a neural network may not beat those simpler tools once prediction overhead is counted. We trained the PyTorch model and compared it with the current guarded rule on unseen cases. Its route decisions were 0.29% slower in Chromium and 1.66% slower in jsdom before inference; JavaScript inference takes about 357ns versus about 10ns for the existing guard on this Node runtime. The tree and direct rule remain better production choices. We do not need ONNX Runtime in production if exporting the tiny model as plain numbers and JavaScript is enough.

References: PyTorch’s ONNX export guide, scikit-learn neural network guide, TensorFlow.js, and Transformers.js.

# Conceptual training loop (not a repository command) features = normalize(training.features) model = SmallNetwork(input_count=len(features[0]), hidden=8, routes=2) for epoch in range(epochs): predicted_log_costs = model(features) measured_log_costs = log(training.costs_ns) loss = mean_squared_error(predicted_log_costs, measured_log_costs) loss.backward() optimizer.step() optimizer.zero_grad()

“Epoch” means one pass over the training examples. The optimizer nudges the network’s numeric weights so its route scores better match the training labels. Repeat passes until held-out training checks stop improving, then save the weights and normalization constants. This is the part people mean by “teaching” this model.

6. Export the model as tiny plain data

For nwsapi, package the few weights and normalization constants as generated JavaScript constants or a compact JSON artifact. Write a small deterministic inference function in JavaScript. Do not download a model, start a Python service, or initialize WebGPU during a normal query. A reasonable first prototype would have a few dozen inputs and hidden values, so its prediction can be compared against the existing decision tree and hand-written route rule.

7. Test CPU first, then test GPU batches separately

Measure the whole decision cost: feature collection + prediction + selected route, and compare it with the existing rule and each route always used. For one query, run prediction on CPU. For batches, separately compare CPU inference with WebGPU dispatch, shader work, and result readback included. If the GPU only wins after batching, expose a batch-planning path; do not pay GPU startup cost for a single selector.

8. Promote only with evidence and a cheap fallback

  • Require exactly identical ordered elements for both routes and the model-selected route.
  • Require a useful held-out speedup in both supported hosts, and set a maximum allowed slowdown for every case.
  • Measure cold queries, small queries, memory, package size, and setup costs as well as warm batches.
  • Guard feature ranges and selector forms. Unknown, missing, non-finite, or out-of-range features use the established route.
  • Keep the model out of production until the benchmark gate passes; preserve the raw examples, hashes, training script, exported weights, and evaluation report so another developer can reproduce it.

What this first run showed

The complete experiment now lives in scripts/repo/bench/planner/neural/. It exports 200 paired observations from two hosts, trains on 96 rows, uses one training family to choose the training duration, and holds out 104 rows from four entire families. It also exports a JavaScript model and measures prediction cost separately. The model did not earn a place in the production runtime: its route choices were 0.29% slower in Chromium and 1.66% slower in jsdom than the existing guarded rule, even before counting the neural decision overhead.

The source timings record battery power, despite the old folder name containing “ac”. The report identifies this as a battery run; it is not AC confirmation. A fresh AC-powered collection can show whether the measurements change when power conditions are controlled.

Glossary

Words used in this guide

Candidate
An element that might satisfy the selector and still needs exact checking.
Feature
A small measured value, such as candidate count, supplied to the planner.
Decision tree
A short sequence of if/else questions that ends with one route choice.
Held-out
Evaluation data kept separate from training so the model faces new examples.
Route
One exact algorithm for finding and checking selector candidates.
Fallback
The established algorithm used when a shortcut is unavailable or outside its measured range.
Speed ratio
Old route time divided by new route time; above 1× means the new route was faster.
